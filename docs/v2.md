# v2: continuous monitoring, regression re-runs and active-deployment billing

Step 6 of a deployment: after launch, Grapim keeps re-running the customer's test set, re-runs it right away
when the customer's system or model version changes, alerts on regressions without paging twice for the
same problem, and meters "active deployments" so they can be billed per month.

Gate this version makes measurable: active deployments keep growing (`usage` per month) and 90-day
retention (`usage` reports how many deployments active three months earlier are still active).

## Configuration (`delomu.json`)

```json
"monitor": {
  "intervalHours": 24,
  "webhookEnv": "ACME_SLACK_WEBHOOK",
  "versionProbe": { "type": "http", "url": "https://api.acme.example/health", "path": "model.version" }
}
```

| Field | Default | Meaning |
| --- | --- | --- |
| `intervalHours` | 24 | Re-run at least this often, even when nothing changed. |
| `webhookEnv` | none | Name of the environment variable that holds the Slack-compatible incoming-webhook URL. The URL is a secret, so it never lives in the file and is never written to the audit log. Without it, alerts are recorded as skipped. |
| `versionProbe` | none | How to ask the customer's AI which version it runs. `{ "type": "http", "url", "path"?, "headers"?, "timeoutMs"? }` does a GET and reads the dot `path` from the JSON (headers may use `${ENV_VAR}`); `{ "type": "command", "command" }` runs in the deployment folder and uses its stdout. |

`<root>/pricing.json` (optional) overrides prices: `{ "platformUsd": 3000, "perActiveDeploymentUsd": 500 }`.

## Commands

```
delomu watch <root> [--once] [--interval-minutes N] [--force] [--no-judge]
delomu usage <root> --month YYYY-MM [--csv FILE]
```

- `watch` finds every folder under `<root>` that holds `delomu.json` (skipping `node_modules`, `runs`,
  `drafts`, `inputs` and dot folders, never following symlinks) and checks each one. `--once` does one pass
  and exits (for cron or a CI schedule); exit code 1 means at least one check failed. Without `--once` it
  loops every `--interval-minutes` (default 15). `--force` re-runs everything on the first pass.
  A deployment whose check fails is reported and does not stop the others.
- `--interval-minutes` is capped at 35791 (the longest timer Node.js can hold).
- `usage` prints invoice lines, the total and the retention figure for a month; `--csv` writes the lines.

## How a check works (`src/v2/monitor.mjs`, `checkDeployment`)

1. **Fingerprint** (`fingerprint.mjs`): SHA-256 over three parts: the bytes of `tests.json`, the `target`
   config as written (key order normalised; `${ENV}` placeholders are hashed, not secrets), and the probed
   version. A failing probe is audited (`monitor.probe.failed`) and keeps the last known version, so a flaky
   health endpoint never looks like a model change.
2. **Due?** Forced, no monitored run yet, fingerprint changed (the reason names which parts), or
   `intervalHours` elapsed since the last monitored run. Otherwise it returns `{ ran: false, reason }`, and the
   reason says when the next run is due.
3. **Run** through v0 `runDeployment`, then **diff** against the latest earlier run (`diff.mjs`): regressions
   (pass to anything else), fixed, new, removed, other status changes, pass-rate delta and verdict change.
   Written to `runs/<id>/diff.json` and `runs/<id>/diff.html` (escaped, same look as the acceptance report).
4. **Alert** (`alerts.mjs`) with incident semantics:
   - The open set is the regressed case ids that are still not passing, plus new regressions.
     "Below acceptance" means the run verdict is `not_accepted`.
   - Dedup key = hash of the sorted open ids and the below-acceptance flag. Same key as the open incident:
     nothing is sent. Different key: an "Updated" alert. Open set empty and back above acceptance: a
     "Resolved" message, and the incident closes.
   - Delivery failures (network error, timeout, non-2xx) are audited as `monitor.alert.failed` and never
     throw; the webhook URL is cut out of the error text. The undelivered message is kept in `monitor.json`
     (`outbox`) and re-sent on every following check, even one that does not re-run the tests, so a webhook
     outage delays a page by one watch interval, not by `intervalHours`. A failed "resolved" keeps the
     incident open until it arrives. A run recomputes the incident and replaces any waiting message.
   - An incident none of whose alerts ever arrived closes silently. Once any alert of it arrived
     (`announced`), clearing always sends "Resolved", even if a later "Updated" alert failed.
5. **State** is written atomically to `<dir>/monitor.json`: fingerprint, its parts, last run id and time,
   last check time, the open incident and any message waiting for a retry. Every check is audited as `monitor.check` (actor `system`), with the
   reason, fingerprint, regression count, pass rate, verdict and any alert type; a check that fails before
   running (bad config, no tests, unreadable previous run) is audited with its error and then thrown.

Payload sent to the webhook (Slack incoming-webhook format; Teams, Mattermost, Discord-compatible relays and
most chat tools accept `text`):

```json
{ "text": "New Grapim alert for Acme / support: 1 regressed case; pass rate 66.7% is below the agreed 90%.",
  "blocks": [ { "type": "section", "text": { "type": "mrkdwn", "text": "..." } },
              { "type": "context", "elements": [ { "type": "mrkdwn", "text": "Comparison report: ..." } ] } ] }
```

## Billing (`src/v2/usage.mjs`, `usage`)

- A deployment is **active** in a month when it has at least one completed run (a run folder with
  `results.json`) whose run id, a UTC timestamp, falls in that month. Monitored runs count, so a deployment
  under `watch` is active every month by construction.
- Each customer (`delomu.json` `customer`) with at least one active deployment pays one platform fee, plus
  one line for its active deployments (quantity times unit price), like a usage-based invoice with a flat
  and a metered price. Customers with no active deployment that month are not billed.
- Prices: defaults, then `<root>/pricing.json`, then the `pricing` option. Unknown fields and negative values
  are rejected so a typo cannot silently bill the default.
- Retention: of the deployments active in month M-3, how many are active in M (`rate` is `null` when there
  were none).
- Folders whose `delomu.json` cannot be read are listed in `skipped` and left out instead of failing the
  whole invoice run. CSV cells starting with `=`, `+`, `-` or `@` are prefixed with `'` so spreadsheet apps
  do not run them as formulas.

## Interfaces for other versions

`src/v2/monitor.mjs` exports `checkDeployment(dir, { now, force, judge, env?, fetchImpl? })`,
`findDeployments(root)` and `usage(root, { month, pricing })`, matching CONTRACT.md. `env` and `fetchImpl`
are optional test and embedding hooks (defaults: `process.env`, global `fetch`). `usage` also returns
`pricing`, `retention` and `skipped`.

## Known limits

- One watcher per deployment root. Two watchers on the same folder can both run a due check; there is no lock.
- Run ids have one-second resolution (v0); two runs of one deployment in the same second share a folder.
- The version probe is only as good as what the customer exposes; without a probe, a silent model swap behind
  an unchanged endpoint is caught by the interval re-run, not immediately.

## Design references

From general knowledge (no pages were opened while building this version):

- **Datadog monitors and synthetic tests**: alert on state transitions, not on every evaluation; send a
  recovery notification when the condition clears; re-notify only when the alert changes; scheduled
  synthetic checks run on a fixed interval regardless of traffic. Borrowed: transition-only alerts,
  "Updated" and "Resolved" messages, interval re-runs alongside change-triggered ones.
- **PagerDuty Events API dedup keys**: events with the same dedup key are grouped into one incident, and a
  resolve event closes it. Borrowed: a dedup key derived from the open set of regressed cases plus the
  below-acceptance flag, and an explicit resolve message.
- **Braintrust and LangSmith experiment comparison**: compare two evaluation runs case by case and show which
  cases regressed and improved, with the score delta. Borrowed: the regressions / fixed / new / removed
  split, keyed by case id, and the pass-rate delta in the comparison report.
- **Stripe usage-based billing**: usage is recorded from events, aggregated per billing period, and priced
  into invoice lines with a quantity and unit amount next to flat subscription fees. Borrowed: usage derived
  from existing run records, a per-month aggregation, and invoice lines (`quantity`, `unitUsd`, `amountUsd`)
  with one flat platform line per customer.
- **Slack incoming webhooks**: `{ text, blocks }` payload, `text` as the notification fallback, mrkdwn
  escaping of `&`, `<`, `>`.
