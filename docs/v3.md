# v3: enterprise and partner edition

v3 turns Delomu from a single-user CLI into a multi-tenant server that an AI startup, its partners and its
enterprise customers can share. It adds orgs, roles, API keys, single sign-on (OIDC), an org-level audit
log with CSV export, a web UI for reviewing agent drafts, and a container image for running inside a
customer's own cloud (VPC).

What this version lets you measure: the share of ARR that comes from enterprise and partner customers.
Enterprise buyers usually require SSO, roles, audit export and self-hosting. Partners (system integrators,
resellers) need to run deployments for several customers from one account.

## Quick start

```sh
export DELOMU_KEY_PEPPER="$(node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))")"
delomu admin bootstrap --org "Acme Partners" --email you@acme.example --kind partner --data ./data
delomu serve --port 8080 --data ./data            # deployments default to ./data/deployments
```

`admin bootstrap` creates the first org, makes you its owner and prints an API key once. It refuses to run
if any org already exists. Then:

```sh
KEY=dk_...   # printed by bootstrap
curl -s localhost:8080/v1/orgs -H "Authorization: Bearer $KEY"
curl -s localhost:8080/v1/orgs/$ORG/deployments -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: 6b1e...' \
  -d '{"name":"support-bot","config":{"target":{"type":"http","url":"https://ai.customer.example/chat","headers":{"authorization":"Bearer ${CUSTOMER_BOT_TOKEN}"},"body":{"message":"{{input}}"},"output":"reply"}},"cases":"id,input,expected,must_include\nr1,Refund please,,refund\n"}'
curl -s -X POST localhost:8080/v1/orgs/$ORG/deployments/support-bot/runs -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' -d '{}'
```

Open `http://localhost:8080/login` and sign in with SSO or the API key.

## Configuration

| Variable / flag | Default | Meaning |
| --- | --- | --- |
| `DELOMU_KEY_PEPPER` | required | Secret (16+ characters) mixed into every API key hash. Keep it in a secret manager. Changing it invalidates every key. |
| `--port` / `PORT` | 8080 | Listen port. |
| `DELOMU_HOST` | 127.0.0.1 | Bind address. The container sets 0.0.0.0. |
| `--data` / `DELOMU_DATA` | `./data` | Holds `delomu.db` (SQLite, WAL mode). |
| `--deployments` / `DELOMU_DEPLOYMENTS` | `<data>/deployments` | Each org's deployments live in `<root>/<orgId>/<name>`. |
| `DELOMU_PUBLIC_URL` | none | External URL, for example `https://delomu.customer.example`. SSO needs it except on localhost. When it starts with `https`, cookies are marked `Secure`. |
| `DELOMU_TRUST_PROXY` | off | Set `1` behind a load balancer: the server then uses the last `X-Forwarded-For` entry (the one your proxy appends) for audit IPs and `X-Forwarded-Proto: https` for `Secure` cookies. |
| `DELOMU_TARGET_ENV_PREFIX` | `CUSTOMER_` | Deployment targets may only use `${VAR}` references that start with this prefix, so a tenant cannot read server secrets such as the pepper. |
| `DELOMU_ALLOW_COMMAND_TARGETS` | off | `command` targets run a shell command on the server. They are refused unless this is `1`. Only turn it on for a single-tenant install you control. |

`createServer({ dataDir, deploymentsRoot, pepper, publicUrl, trustProxy, allowCommandTargets, targetEnvPrefix, maxBodyBytes, rateLimit: { capacity, refillPerSec }, judge, fetch, now, env, log })`
returns an `http.Server` that is not listening yet. `start(port, options)` also listens and resolves to the server. Options left out fall back to the environment, so `start(port)` works with `DELOMU_DATA` (and optionally `DELOMU_DEPLOYMENTS`) and `DELOMU_KEY_PEPPER` set.

`node:sqlite` on Node 24.19 does not print an experimental warning. On older Node lines that still mark it
experimental, Node prints an `ExperimentalWarning` once at startup. Delomu leaves that warning alone; it does
not affect behaviour.

## Data model

SQLite at `<data>/delomu.db`. Migrations only move forward and are recorded in `schema_migrations`. A server
refuses to open a database whose schema is newer than the server's own.

| Table | Purpose |
| --- | --- |
| `orgs` | `kind` is `customer` or `partner`. `partner_org_id` links a customer org to the partner that manages it. |
| `users` | One row per email address (case-insensitive). |
| `memberships` | `(org, user) -> role`. |
| `api_keys` | `dk_` keys. Stores only `HMAC-SHA256(pepper, key)`, a display prefix, scopes, `last_used_at` and `revoked_at`. |
| `sessions` | Web sessions. Stores the SHA-256 of the cookie token and a CSRF token per session. Sessions last 12 hours. |
| `oidc_configs` | Per-org issuer, client id, the *name* of the env var that holds the client secret, allowed email domains and the default role. |
| `oidc_logins` | Pending sign-ins: hashed state, nonce and PKCE verifier. They expire after 10 minutes and each can be used once. |
| `audit_events` | Org-level events: actor, action, target, detail, IP. |
| `idempotency_keys` | Stored responses for retried POSTs. Kept for 24 hours. |
| `deployments` | Which deployment folders are registered to which org. |

## Roles and permissions

| Permission | owner | admin | engineer | reviewer | viewer |
| --- | :-: | :-: | :-: | :-: | :-: |
| `org:read` | yes | yes | yes | yes | yes |
| `org:manage` (SSO config, create customer orgs as a partner) | yes | yes | | | |
| `members:read` | yes | yes | yes | yes | yes |
| `members:manage` | yes | yes | | | |
| `keys:manage` | yes | yes | | | |
| `deployments:read` | yes | yes | yes | yes | yes |
| `deployments:write` | yes | yes | yes | | |
| `runs:read` | yes | yes | yes | yes | yes |
| `runs:create` | yes | yes | yes | | |
| `conversations:write` (send live conversations to check) | yes | yes | yes | | |
| `guard:check` (check a reply before the customer sees it) | yes | yes | yes | | |
| `drafts:read` | yes | yes | yes | yes | yes |
| `drafts:review` (approve, edit, reject) | yes | yes | yes | yes | |
| `audit:read` (events, CSV export, deployment logs) | yes | yes | | yes | |
| `usage:read` | yes | yes | | | |

Additional rules:

- Only an owner can grant, change or remove the owner role, and an org always keeps at least one owner.
- Removing a member revokes that member's keys and ends their sessions in the org. Revoking a key also ends
  any web session that was signed in with it.
- **Partners.** Owners and admins of a partner org act as `admin` in every customer org that partner
  manages. They can create new customer orgs with `POST /v1/orgs`. Partner engineers, reviewers and viewers
  get no access to customer orgs. A customer org never sees its partner org or any sibling customer.
- **Isolation.** An org you cannot access answers `404`, not `403`, so a valid org id reveals nothing.
- **API keys** act as the user who created them, in the org they were created in. They can only be created
  in an org where you are a direct member, so a partner cannot create keys inside a customer's org.
  `scopes` (a list of the permissions above) restricts a key below its user's role, and the role is
  re-checked on every request. A restricted key can only create keys that are at least as restricted as
  itself.

## API (`/v1`)

Authentication: `Authorization: Bearer dk_...`. Bodies are JSON (1 MB limit). Every error has this shape:

```json
{ "error": { "type": "invalid_request_error", "message": "name must be ...", "param": "name" } }
```

Error types: `invalid_request_error` (400, 405, 413), `authentication_error` (401), `permission_error`
(403), `not_found_error` (404), `conflict_error` (409), `idempotency_error` (409 while the first request is
still running, 422 when the key is reused with a different body), `rate_limit_error` (429, with
`Retry-After`) and `api_error` (500, or 501 with `code: not_implemented`).

**Idempotency.** Send `Idempotency-Key` (1–255 printable characters) on any POST. A retry with the same key
and the same body replays the stored status and body, with the header `Idempotent-Replayed: true`. Keys are
scoped to the API key that sent them. Client errors are stored and replayed. Server errors are not stored,
so the client can retry them.

**Lists** return `{ object: "list", data, has_more, next_cursor }`. Pass `?limit=1..100&cursor=...` to page.

**Rate limit.** Each API key gets a token bucket (default: burst of 120, refilled at 2 per second).

| Method and path | Permission |
| --- | --- |
| `GET /v1/orgs` · `POST /v1/orgs {name}` | any member · partner owner/admin |
| `GET /v1/orgs/:org` | `org:read` |
| `GET` / `PUT /v1/orgs/:org/sso {issuer, client_id, client_secret_env?, allowed_domains, default_role?}` | `org:manage` |
| `GET` / `POST /v1/orgs/:org/members {email, role}` · `PATCH /members/:user {role}` · `DELETE /members/:user` | `members:read` / `members:manage` |
| `GET` / `POST /v1/orgs/:org/api_keys {name, scopes?}` · `DELETE /api_keys/:id` | `keys:manage` |
| `GET` / `POST /v1/orgs/:org/deployments {name, config?, cases?}` · `GET /deployments/:name` | `deployments:read` / `deployments:write` |
| `GET` / `POST /v1/orgs/:org/deployments/:name/runs {judge?}` · `GET /runs/:id` · `GET /runs/:id/report.html` | `runs:read` / `runs:create` |
| `POST /v1/orgs/:org/deployments/:name/conversations {message, answer, id?, at?, source?}` · `GET /conversations?month=&status=` | `conversations:write` / `runs:read` |
| `POST /v1/orgs/:org/deployments/:name/guard {message, reply, id?}` (see `docs/v5-guard.md`) | `guard:check` |
| `GET /v1/orgs/:org/deployments/:name/drafts?status= · `GET /drafts/:id` · `POST /drafts/:id/review {decision, note?, content?}` | `drafts:read` / `drafts:review` |
| `GET /v1/orgs/:org/deployments/:name/audit` (entries and hash-chain `verify`) | `audit:read` |
| `GET /v1/orgs/:org/audit_events` · `GET /v1/orgs/:org/audit_events.csv` | `audit:read` |
| `GET /v1/orgs/:org/usage?month=YYYY-MM` (from v2 when installed, otherwise 501) | `usage:read` |
| `GET /healthz` | none |

Endpoint notes:

- **Deployment names** must be 1–63 lowercase letters, digits or dashes. Windows device names are refused.
  The server re-checks every resolved path against the org's folder. A folder an operator already placed
  under `<root>/<orgId>/<name>` can be registered without `config`.
- **Runs** execute synchronously and return the run summary. The LLM judge is off unless `judge: true`.
  Only one run per deployment can be in progress at a time; a second one gets 409.
- **Draft review** loads every file in `src/commands/` first, so all draft appliers (v1, v4, ...) are
  registered. Reviews are written to the deployment's `audit.jsonl` as `human:<email>` and to the org's
  audit events.
- **CSV export** puts org events and every deployment's `audit.jsonl` in one file, with each chain's
  status (`intact` or `broken at N`). Cells that start with `= + - @` are prefixed with `'` so spreadsheets
  do not run them as formulas.

## Single sign-on (OIDC)

1. In your IdP (Okta, Entra ID, Google Workspace, Auth0, ...), create an OIDC web application. Set the
   sign-in redirect URI to `https://<DELOMU_PUBLIC_URL>/sso/callback`, use the authorization code grant,
   and turn on PKCE.
2. Put the client secret in an env var on the server, for example `OKTA_CLIENT_SECRET`. The database stores
   only the variable's name.
3. Configure the org with `PUT /v1/orgs/:org/sso`, for example
   `{"issuer":"https://acme.okta.com","client_id":"0oa...","client_secret_env":"OKTA_CLIENT_SECRET","allowed_domains":["acme.com"],"default_role":"viewer"}`.
4. Users sign in at `/login` with the org's slug.

The flow is authorization code with PKCE (S256), plus `state` and `nonce`. `state` is single-use, expires
after 10 minutes and is bound to the browser by a short-lived cookie. Client authentication uses
`client_secret_basic`, falling back to `client_secret_post` if that is all the provider supports. Without a
secret, the client is treated as public and relies on PKCE alone.

The ID token must pass every one of these checks:

- It is signed with RS256 by a key in the provider's JWKS. The JWKS is cached and fetched again when an
  unknown `kid` appears.
- `iss` exactly matches the discovery issuer.
- `aud` contains the client id. When there are several audiences, `azp` must equal the client id.
- `exp` has not passed and `iat` is not in the future. Both allow 60 seconds of clock skew.
- `nonce` matches the one sent with the request.
- `email` is present, `email_verified` is not false, and the email's domain is in `allowed_domains`.

Accepted users are added just in time with `default_role`, which can never be `owner`. Successful and failed
logins both go to the audit log. Providers must use https; plain http is accepted only for localhost.

## Web UI

`/login` offers SSO or an API key. The other pages are:

- `/`: the orgs you can access.
- `/orgs/:org`: deployments.
- `/orgs/:org/deployments/:name`: runs, with links to each report.
- `/orgs/:org/deployments/:name/drafts`: review. You can approve as-is, approve after editing the JSON, or
  reject, each with a note.
- `/orgs/:org/audit`: org events and each deployment's chain status.

Security measures:

- Every value on these pages is HTML-escaped.
- Pages are served with a strict CSP (`default-src 'none'`), `X-Frame-Options: DENY` and `no-store`.
- The session cookie is `HttpOnly; SameSite=Lax`, and `Secure` behind https.
- Every form POST, including sign-in and sign-out, checks a CSRF token.

## Self-hosting in a customer VPC

The image is the usual choice for enterprise buyers who will not send their cases or their AI's answers to
a vendor cloud. It holds no secrets or data; both come from outside.

```sh
docker build -t delomu:v3 .
docker volume create delomu-data
docker run -d --name delomu -p 8080:8080 -v delomu-data:/data \
  -e DELOMU_KEY_PEPPER -e DELOMU_PUBLIC_URL=https://delomu.internal.customer.example \
  -e DELOMU_TRUST_PROXY=1 -e OKTA_CLIENT_SECRET -e CUSTOMER_BOT_TOKEN delomu:v3
docker exec delomu node bin/delomu.mjs admin bootstrap --org "Customer Inc" --email admin@customer.example
```

- **Image.** `node:24-slim`, runs as the non-root `node` user, `/data` volume, `HEALTHCHECK` on
  `GET /healthz`, and only production dependencies.
- **Network.** Put the container in a private subnet behind the customer's load balancer or ingress, and
  terminate TLS there (then set `DELOMU_TRUST_PROXY=1`). Outbound traffic only needs to reach the
  customer's AI endpoint, their IdP and, if the judge is used, the Anthropic API. Everything else can be
  blocked by egress rules.
- **Secrets.** Inject `DELOMU_KEY_PEPPER`, the OIDC client secret and the `CUSTOMER_*` target tokens from
  the customer's secret manager (Kubernetes Secrets, AWS Secrets Manager, Vault). Never bake them into the
  image or `delomu.json`.
- **Backups.** Snapshot the `/data` volume. For a consistent SQLite copy while the server is running, use
  `sqlite3 delomu.db ".backup backup.db"`. The deployment folders are plain files.
- **Scaling.** Run one replica per data volume. SQLite, the rate limiter and the run lock are local to the
  process; see "Known limits".
- **Upgrades.** Pull the new image and restart; migrations run at startup. Take a backup first. Rolling back
  to an older image after a migration is refused on purpose.

## Design references

- Stripe API. Ideas taken: versioned `/v1` paths; one error object with `type`, `message`, `code` and
  `param`; idempotency keys of up to 255 characters, compared with the original parameters and pruned after
  24 hours; `object: "list"` with `has_more` and cursor paging; restricted keys shown once.
  Opened: <https://docs.stripe.com/api/idempotent_requests> and <https://docs.stripe.com/api/errors>.
  Where we differ: Stripe also replays 500 responses, but Delomu does not store them so the client can
  retry; a reused key with a different body returns 422; and a request still in progress returns 409. The
  422 and 409 statuses follow the IETF Idempotency-Key header draft (from general knowledge).
- OpenID Connect Core 1.0, section 3.1.3.7 (ID token validation). The checks on `iss`, `aud`, `azp`, alg,
  `exp`, `iat` and `nonce` follow it. Opened: <https://openid.net/specs/openid-connect-core-1_0.html>.
  PKCE S256 follows RFC 7636 (from general knowledge).
- Okta and WorkOS SSO setup, from general knowledge: a per-org connection, the client secret held outside
  the app, just-in-time provisioning with a default role, and an allow-list of email domains.
- GitHub and Linear organizations, from general knowledge: a small fixed set of roles; an owner role that
  only owners can grant; at least one owner kept; returning 404 rather than 403 for resources you cannot see.
- Vanta and Drata style evidence export, from general knowledge: an append-only event log with actor, IP
  and target; a CSV export that includes integrity status; protection against CSV formula injection.
- HashiCorp and Snowflake partner and reseller models, from general knowledge: a partner account that
  manages customer accounts with delegated admin rights, without becoming a member of them.
- GitLab self-managed, from general knowledge: one container plus a data volume, configured through
  environment variables, a health check endpoint, migrations at boot, and backups documented as a volume
  snapshot.

## Known limits

- Rate limits and the run lock live in memory in one process. Running several replicas would need a shared
  store such as Postgres or Redis.
- Runs are synchronous HTTP requests. Very large test sets should be run with `delomu run` or the v2 watcher
  until runs become background jobs.
- `CUSTOMER_*` environment variables are shared by every org on one server. Multi-tenant hosts that need
  separate per-tenant target secrets should run one install per tenant (the VPC model) until per-org secret
  references are added.
- HTTP targets can reach any address the server can reach. In a shared install, restrict this with egress
  rules.
- Org audit events are append-only in the application, but they are not hash-chained like
  `audit.jsonl`.
- There is no SCIM deprovisioning. Removing a user from the IdP stops new logins, but existing sessions run
  until they expire (12 hours) unless an admin removes the member.
