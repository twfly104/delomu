# v4: deployment knowledge library

Every deployment makes the next one faster. When a customer agrees, Delomu harvests that deployment's test
cases, integration shape and recurring failure patterns into a shared library. It removes personal data and
secrets first. Later deployments search the library and get suggested test cases as a draft that an engineer
reviews.

Gate it measures: new deployments get faster. Compare v0/v1 `hours` for step 3 on deployments that used
`library suggest` with those that did not.

## Commands

```
delomu library harvest <dir> --library DIR [--by NAME]
delomu library search <query> --library DIR [--kind case|integration|failure] [--tag T] [--limit N]
delomu library suggest <dir> --library DIR [--limit N]
delomu library forget <sourceHash> --library DIR
delomu library stats --library DIR
```

`harvest` needs the environment variable `DELOMU_LIBRARY_SALT`, a random secret of at least 16 characters.
Everyone who writes to the same library must use the same salt. Keep it in a secret manager, never in a file.

## Consent (required before any harvest)

`delomu.json`:

```json
{
  "industry": "fintech",
  "library": {
    "consent": true,
    "consentedBy": "Jane Roe, DPO",
    "consentedAt": "2026-10-01",
    "names": ["Globex", "Hank Scorpio"],
    "patterns": { "ORDER": "ORD-\\d{5}", "ACCOUNT": "\\bAC-\\d{5}\\b" }
  }
}
```

- Harvest is refused unless `consent` is exactly `true`, `consentedBy` is set, and `consentedAt` is a real
  date that is not in the future. The refusal is written to the deployment's `audit.jsonl` as
  `library.harvest.refused`.
- Every harvest is written to the deployment's audit log (`library.harvest`: source hash, entry counts,
  redaction counts, who consented and when) and to the library's own `audit.jsonl` (source hash and counts
  only).
- `consentedBy` stays in the deployment folder. It is never copied into the library.

## De-identification (`scrub`)

`scrub(text, { names, patterns }) -> { text, found }` replaces each detected item with a typed placeholder
and counts it. It runs offline, gives the same output for the same input, and never scans a placeholder a
second time.

| Kind | Placeholder | How it is detected |
| --- | --- | --- |
| URL credentials and query strings | `https://[CREDENTIALS]@host/path?[QUERY]` | The host and path stay; `user:pass@`, `?…` and `#…` are removed |
| email | `[EMAIL]` | Address shape |
| secret | `[SECRET]` | `Bearer/Basic/Token <value>` when the value is not a plain word (it has a digit, base64 punctuation or inner capitals); `sk-`, `rk_`, `pk_`, `dk_`, `ghp_`, `xox?-`, `AKIA…`; JWTs; hex strings of 32+ characters; base64 runs of 32+ characters that mix upper case, lower case and digits. `${ENV_VAR}` references stay |
| custom (`library.patterns`) | `[ORDER]`, `[ACCOUNT]`, … | Your own regexes, matched without regard to case. Invalid names, invalid regexes and regexes that match empty text are rejected |
| iban | `[IBAN]` | Country code plus check digits; mod-97 validated; spaced or compact |
| card | `[CARD]` | 13 to 19 digits, with or without spaces or dashes; Luhn validated |
| ssn | `[SSN]` | Dashed US form only; area 000, area 666, area 9xx, group 00 and serial 0000 are excluded |
| ip | `[IP]` | IPv4, and IPv6 checked with `net.isIPv6`. An IPv4-shaped value after `v`, `version`, `build` or `release` is kept |
| phone | `[PHONE]` | `+` or `00` international numbers with 8 to 15 digits (E.164). Without `+`: 9 to 15 digits with phone-style separators |
| name | `[NAME]` | `library.names` plus the `customer` value. Whole words only, ignoring case, longest name first |

Text that is deliberately kept, with a test for each case: prices (`$1,299.99`, `1234567.89`), dates
(`2026-10-31`, `31/10/2026`), times, version numbers (`v2.3.1`, `version 1.2.3.4`), ranges such as `5-10`,
short ids, bare digit runs such as Unix timestamps, `{{input}}` and `${ENV_VAR}`.

Known limits: free-text street addresses and person names are removed only when they are listed in
`library.names`. A bare 10-digit number written without separators is not treated as a phone number; add a
pattern if the customer writes phone numbers that way.

## What a harvest stores

`<libraryDir>/entries.jsonl`, one JSON object per line:

| Field | Meaning |
| --- | --- |
| `id` | Content hash (16 hex). Stable when the same content is harvested again |
| `kind` | `case`, `integration` or `failure` |
| `case` fields | `input`, `expected`, `must_include`, `must_not_include`, `regex`, `tags`. Taken only from valid rows of `cases.csv` (the same rows `delomu tests` uses), all scrubbed. A `regex` that would need scrubbing is dropped (a placeholder inside a regex is a character class), and a row left with no check is skipped |
| `integration` fields | `template`: the `delomu.json` target with every header value set to `[VALUE]`, the URL host set to `[HOST]`, the query removed and other strings scrubbed. `summary`: searchable text describing the integration |
| `failure` fields | `checkType`, `pattern` (the failed check reason, scrubbed, with numbers replaced by `#`), `cases` (distinct failing cases), `occurrences` (across all runs), `tags` |
| `sourceSystems` | System names from `mapping.json`, scrubbed and lower-cased |
| `industry` | `delomu.json` `industry`, lower-cased |
| `source` | First 32 hex characters of HMAC-SHA256(salt, customer + deployment name) |
| `createdAt` | Harvest time |

Case ids from the customer are not stored, because they can contain order numbers. Harvesting the same
deployment again replaces all of its earlier entries, so the library reflects the deployment's current state.
Writes take a lock file (a lock older than 10 minutes counts as stale) and replace `entries.jsonl`
atomically.

## Search and suggest

- `search(libraryDir, query, { limit, kind, tags, industry })` ranks entries with Okapi BM25 (k1 = 1.2,
  b = 0.75). Tokens are lower-case Unicode letter and digit runs, and stop words are dropped. Equal scores
  keep library order.
- `suggest(dir, { libraryDir, limit })` builds a query from the deployment's cases, tags, mapping and
  industry. If the deployment has no cases yet, it reads `inputs/*.md|txt|csv|json` instead. It ranks library
  `case` entries and boosts the score by 50% for the same industry, 25% per shared source system (up to 2) and
  10% per shared tag (up to 3). It skips:
  - the deployment's own entries (when the salt is set);
  - cases whose scrubbed input it already has in `cases.csv`;
  - cases already proposed in a pending `cases` draft, or in one an engineer rejected.

  The result is a pending draft of the shared kind `cases` (step 3). Each row has the id `lib-<8 hex>` and the
  tag `from-library`. The rationale lists the matched terms and boosts for every row. `suggest` never writes
  `cases.csv`. When an engineer approves the draft, v1's `cases` applier appends the rows. If nothing new
  matches, `suggest` returns `null` and no draft is created.

## Deletion

`forget(libraryDir, sourceHash)` deletes every entry from one deployment and records `library.forget` in the
library's audit log. `harvest` prints the source hash, and the deployment's own audit log records it. If a
customer withdraws consent, set `"consent": false` so future harvests are refused, then run `forget`.

## Module layout

- `src/v4/scrub.mjs`: detectors and validators (Luhn, IBAN mod-97)
- `src/v4/bm25.mjs`: tokenizer and BM25 ranking
- `src/v4/store.mjs`: `entries.jsonl` storage, lock, `forget`, `stats`, library audit
- `src/v4/deployment.mjs`: reads a deployment: raw config, consent, privacy options, source hash, cases, mapping
- `src/v4/harvest.mjs`, `src/v4/suggest.mjs`: the two flows
- `src/v4/library.mjs`: the public interface from CONTRACT.md, plus `search`
- `src/commands/v4.mjs`: the `library` command

## Design references

Pages opened while designing:

- Zendesk, "Automatically detecting sensitive information for redaction":
  https://support.zendesk.com/hc/en-us/articles/6669399593882-Automatically-detecting-sensitive-information-for-redaction
  Borrowed: a fixed list of typed detectors (email, card, IBAN, SSN, IP, phone, names) plus up to a few
  customer-defined regex patterns, and an event-log record for every redaction. A Zendesk search summary
  said card detection uses the Luhn algorithm; Delomu does the same and adds mod-97 for IBANs.
- Stripe Radar, https://stripe.com/gb/radar. Borrowed: present the network effect (patterns pooled across
  many customers make each new one better) as the product's value. That page does not describe consent
  controls. Delomu adds an explicit, recorded, per-deployment opt-in, plus deletion.

From general knowledge (no page opened):

- Glean: index entries carry their permission scope and are filtered at query time. Here the scope is
  "consented and de-identified": only consented deployments are harvested, and `search` can filter by
  industry, kind and tags.
- Gong: redact at ingestion rather than at display, so raw PII never reaches the shared store. Harvest
  scrubs before anything is written.
- Plaid: data from one customer is linked by a pseudonymous identifier so that a deletion request can remove
  all of it. Here that identifier is the salted `source` hash and `forget` removes the entries.
